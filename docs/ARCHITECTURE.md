# Architecture

Technical reference for how safespeak-admin is put together. For setup/commands and the product-level "why," see the root [README](../README.md).

## Layering

```
app/ (routes)
  -> hooks/ (useLiveQuery-backed data hooks)
    -> components/providers/repository-provider.tsx (React context)
      -> lib/repositories/admin-content-repository.ts (interface)
        -> lib/repositories/indexeddb-admin-content-repository.ts (implementation)
          -> lib/db/db.ts (Dexie schema)
            -> lib/models/*.ts (Zod schema + TS type per domain)
```

Rule: **page and component code never imports `lib/db/db.ts` or Dexie directly.** It goes through a hook, which goes through the repository interface. This is what makes `lib/repositories/indexeddb-admin-content-repository.ts` swappable later.

## Dexie schema (`DB_SCHEMA_VERSION = 1`)

| Table | Indexed fields | Notes |
| --- | --- | --- |
| `documents` | `id, status, sourceType, processingStatus, createdAt, updatedAt` | May carry a `fileBlob` (raw PDF bytes), written outside the Zod-validated path — see below. |
| `documentChunks` | `id, documentId, chunkIndex, createdAt` | Local chunk-preview records, see `lib/pdf/chunk-text.ts`. |
| `microcards` | `id, status, topic, createdAt, updatedAt` | Full CRUD (Phase 4) — see "Microcards & Rights and Legal Information" below. `topic` is a legacy Phase 1 field, preserved (still lightly exposed) but distinct from the newer typed `cardType`. |
| `rightsContent` | `id, status, jurisdiction, createdAt, updatedAt` | Full CRUD (Phase 4). `jurisdiction` was upgraded this phase from free text to the same typed `AUSTRALIAN_JURISDICTION_VALUES` enum Knowledge & Legislation uses (two Phase 1 seed rows using the old free-text placeholder were migrated to real jurisdiction codes at the same time). |
| `supportOrganisations` | `id, status, createdAt, updatedAt` | Full CRUD (Phase 5) — see "Support Directory" below. |
| `supportProfessionals` | `id, status, professionalType, verificationStatus, createdAt, updatedAt` | Full CRUD (Phase 5). May carry a `profileImageBlob`, written outside the Zod-validated path — same pattern as `documents.fileBlob` above. |
| `reportingDestinations` | `id, status, createdAt, updatedAt` | Full CRUD (Phase 5). Not indexed on jurisdiction — `jurisdiction` (singular, free text) was upgraded to `jurisdictions` (typed `AUSTRALIAN_JURISDICTION_VALUES[]`) plus an `australiaWide` flag, and nothing queries this table by jurisdiction (every list/filter/eligibility read does `.toArray()` and filters in JS, same as the boolean fields below), so the stale single-value index was removed rather than left pointing at a field that no longer exists. |
| `incidentTypes` | `id, name, createdAt` | Full CRUD (Phase 3) — see "Taxonomy" below. |
| `triageLabels` | `id, urgencyLevel, createdAt` | Full CRUD (Phase 3). `urgencyLevel` is a legacy Phase 1 field, preserved (and still used by `matchingRuleSchema`) but not exposed in the Phase 3 form — superseded by `labelGroup`. |
| `resourceCategories` | `id, parentCategoryId, createdAt` | Full CRUD (Phase 3). `parentCategoryId` is a legacy Phase 1 field, preserved on the schema but not exposed anywhere in the Phase 3 UI — category hierarchy is out of scope. |
| `matchingRules` | `id, incidentTypeId, createdAt` | Data contract + demo records only — no rule-builder UI. |
| `auditEvents` | `id, entityType, entityId, action, timestamp` | Append-only. |
| `appSettings` | `id` | Single row, `id: "app-settings"`. |
| `contentBundleHistory` | `id, generatedAt` | One row per completed export. |

**Boolean fields (`isDemo`, `verified`, `active`, ...) are never indexed.** IndexedDB does not accept `boolean` as an index key type — attempting to index one throws at the browser level. Where a query needs to filter on a boolean, the repository loads with `.toArray()` (or an indexed prefilter on another field) and filters in JS. Given the seeded/demo dataset sizes involved (tens of records per table), this has no meaningful performance cost.

**Migrating the schema:** add a new `.version(N).stores({...})` block to `AdminDatabase` in `lib/db/db.ts`; do not edit an existing version block. Dexie applies versions in order and runs any `.upgrade()` callback attached to the new version against existing data.

## Repository interface

`AdminContentRepository` (`lib/repositories/admin-content-repository.ts`) exposes:

- One `CrudRepository<T>` (`list/get/create/update/remove`) per content domain.
- `documents` additionally exposes, beyond the generic CRUD:
  - `setFileBlob` / `getFileBlob` — **outside** the Zod-validated `create`/`update` path, because `Blob` is not JSON-serializable and therefore not part of the persisted-data contract used for bundle export. Writing it through `documentSchema.parse()` would silently strip it.
  - `applyExtractionResult(id, result, audit)` — one Dexie transaction (`documents` + `documentChunks` + `auditEvents`) that commits file metadata, replaces chunks, and appends an audit event together. The single commit point for create/replace/retry extraction outcomes — see "Document extraction orchestration" below.
  - `transitionStatus(id, nextStatus, actor)` — validates the status graph + `legislationPublishGuard`, updates status, appends an audit event, atomically. Throws `StatusTransitionError`.
  - `updateWithVersionCheck(id, patch, expectedVersion, actor)` — throws `VersionConflictError` if the stored `version` no longer matches `expectedVersion` (a stale-write guard for the same document being edited in two tabs).
  - `deleteDraft(id, actor)` — throws `InvalidDeletionError` unless `status === "draft"`; deletes the document row (and its `fileBlob`), its chunks, and appends an audit event in one transaction.
  - `listOverdueForReview()`.
- `getRagReadinessSummary()` — top-level, aggregates `lib/legislation/readiness.ts`'s `summarizeReadiness()` over `documents.list()`.
- `documentChunks.listForDocument` / `replaceForDocument`.
- `auditEvents.list` / `append` (append-only; there is no `update`/`remove`).
- `settings.get` / `update` (lazily creates the single settings row on first read).
- `bundleHistory.list` / `append`.
- `getDashboardSummary()` — aggregates counts across domains for the Dashboard page.
- `ensureSeeded()` — idempotent; seeds demo data once, no-ops afterward.
- `resetDemoData()` — deletes every `isDemo: true` row per table (including chunks belonging to demo documents), then re-seeds, then records an audit event.

`createCrudRepository<T>()` (private to `indexeddb-admin-content-repository.ts`) implements the generic CRUD boundary once and is reused for every domain rather than hand-writing ten near-identical repositories. The typed errors above (`src/lib/repositories/errors.ts`) let calling UI code distinguish "this specific rule blocked the action" from a generic failure without string-matching an error message.

### Taxonomy repository (`TaxonomyRepository<T extends TaxonomyEntity>`)

A second generic factory, `createTaxonomyRepository<T>()`, layered on top of `createCrudRepository<T>()` and shared by `incidentTypes`, `triageLabels`, and `resourceCategories` — each still backed by its **own** typed Dexie table (`db.incidentTypes` / `db.triageLabels` / `db.resourceCategories`), never a shared untyped table. `T extends TaxonomyEntity` (`lib/taxonomy/types.ts`, `{ id, name, machineKey, status, displayOrder }`) is the one shared constraint every generic taxonomy component, hook, and repository method is written against — introduced specifically to stop the three call sites (status actions, row actions, replace-references dialog, the two data hooks) from each declaring their own slightly-different local structural type and drifting apart.

Beyond `CrudRepository<T>`, it adds:

- `create(record)` — checks `isDuplicateMachineKey` first (throws `DuplicateMachineKeyError`), then writes inside one transaction with an audit event. Does **not** run the publish-blocker guard — a fresh record is written at whatever status its caller already chose; see "Publishing workflow" below for why that's still safe.
- `updateWithVersionCheck(id, patch, expectedVersion, actor)` — same stale-write guard as the CRUD-level method, plus one taxonomy-specific rule: `machineKey` is unconditionally deleted from `patch` before it reaches `schema.parse()`, so a caller cannot smuggle a key change through even by constructing the patch object directly.
- `transitionStatus(id, nextStatus, actor)` — recomputes the full blocker list against every *other* existing record of that type (needed for the duplicate-key/name checks in `lib/taxonomy/eligibility.ts`), wraps it in `taxonomyPublishGuard(blockers)`, and runs it through the same `canTransitionStatus` used by every other domain. Throws `StatusTransitionError`.
- `deleteDraft(id, actor)` — throws `InvalidDeletionError` unless the record is `draft` status **and** its live usage count (via `computeTaxonomyUsage`, recomputed against a fresh data bundle, never a cached count) is zero.
- `reorder(orderedIds, actor)` — one transaction that assigns sequential `displayOrder` values matching the given id order, plus one audit event for the whole operation (not one per record).
- `isMachineKeyTaken` / `isDisplayNameTaken` / `listActiveReplacementTargets` (non-archived, excluding self) / `getUsage(id)` / `replaceReferences(sourceId, targetId, actor, archiveSourceAfter)` — see README "Replace References."

`applyReferenceReplacementPlan(db, kind, plan, actor)` is the piece that actually writes a `ReferenceReplacementPlan` entry to the right Dexie table/field — a `switch` on `(entityType, kind)` covering every `ReferenceSource` the dependency service knows about, using a small generic `bumpVersion<R extends { id: string; version: number }>` helper so every write goes through the same version-increment path.

### Publishable content repository (`PublishableContentRepository<T>`)

A third generic factory, `createPublishableContentRepository<T>()`, added in Phase 4 for `microcards` and `rightsContent` and widened in Phase 5 to also serve `supportOrganisations`, `supportProfessionals`, and `reportingDestinations` (five domains total) — the counterpart to `createTaxonomyRepository<T>()` for domains that need dependency-protected hard delete and a publish-blocker guard but have **no** machine key and **no** Replace References workflow. `T extends { id, status, isDemo, createdBy, updatedBy, version }` is the shared constraint — Phase 4's version also required a `title: string` field (audit summaries used `record.title`), but that broke down the moment a third entity's natural label field wasn't named `title` (Support Organisation uses `name`, Advocate/Counsellor uses `fullName`/`displayName`, Reporting Destination uses `name`). Phase 5 removed the `title` requirement from `PublishableContentRecordShape` and added a `getLabel: (record: T) => string` parameter to the factory instead, so every caller supplies its own label-extraction function rather than the type forcing a specific field name to exist. The shared `PublishableStatusActions`/`PublishableRowActions` components were widened the same way — from requiring `record.title` to taking an explicit `label: string` prop — with all five call sites updated together so none of them silently regressed.

Beyond `CrudRepository<T>`, it adds:

- `create(record)` — writes inside one transaction with an audit event. No machine-key check (there is none).
- `updateWithVersionCheck(id, patch, expectedVersion, actor)` — same stale-write guard as every other domain; no machine-key-stripping step (nothing to strip).
- `transitionStatus(id, nextStatus, actor)` — fetches the eligibility context (`buildTaxonomyDataBundle`) **before** opening the transaction — a Dexie transaction can only touch the tables explicitly listed in its own scope, and this context read touches far more tables (documents, resource categories, support organisations, the other of the two domains) than the narrow `[table, auditEvents]` scope the actual status write needs. This mirrors the fix already applied to every domain's `deleteDraft()` (see below) and is the same reason `deleteDraft` also fetches its context first. Runs the same `taxonomyPublishGuard(blockers)` / `canTransitionStatus` every other domain uses, fed by `getMicrocardBlockers` / `getRightsContentBlockers` (`lib/microcards/eligibility.ts`, `lib/rights-content/eligibility.ts`) instead of `lib/taxonomy/eligibility.ts`'s functions. Also sets `publishedDate` automatically, once, the first time a record reaches `published` — never overwritten on a later transition (e.g. `published -> needs_update -> published` again keeps the original `publishedDate`).
- `deleteDraft(id, actor)` — same pattern as taxonomy: throws `InvalidDeletionError` unless `draft` status and zero current usage (`computeTaxonomyUsage(kind, id, bundle)`, where `kind` is one of `"microcard" | "rights_content"` (Phase 4) or `"support_organisation" | "support_professional" | "reporting_destination"` (Phase 5) — see "Dependency service" below).
- `getUsage(id)` — same `computeTaxonomyUsage` call, exposed directly (there is no Replace References workflow to hide it behind).

`microcards` additionally gets a `reorder(orderedIds, actor)` method, added as a one-off intersection type in `admin-content-repository.ts` (`PublishableContentRepository<Microcard> & { reorder(...) }`) rather than folded into the shared interface — Rights & Legal Information has no display-order concept, so a generic `reorder` on `PublishableContentRepository<T>` would be dead weight on that domain. The implementation is inlined at the `microcards` instantiation site in `indexeddb-admin-content-repository.ts` (same displayOrder-reassignment-plus-one-audit-event logic as taxonomy's `reorder`, just not extracted into the shared factory since only one of the factory's two callers needs it).

Every eligibility-context fetch across both new repository methods reuses the *same* `buildTaxonomyDataBundle()` closure the taxonomy repositories already call — `TaxonomyDataBundle` already carries every field either domain's eligibility module needs (`resourceCategories`, `documents`, `supportOrganisations`, `rightsContent`), so no second, parallel data-bundle type or fetch function was introduced.

## Validation boundary

Every record that crosses the IndexedDB boundary — read from storage, seeded, or exported into a bundle — passes through its domain's Zod schema:

- **Read path** (`lib/db/validation.ts`): `filterValidRecords` drops individually-invalid rows and returns the rest; `parseStoredRecord` is the single-record version. In development, dropped records log their Zod issues to the console (`console.warn`); production never surfaces a raw stack trace.
- **Seed path** (`lib/db/seed.ts`): every seed array is `.map(schema.parse)`'d at module load, so a malformed literal fails immediately during development rather than being silently stored.
- **Export path** (`lib/bundle/export-bundle.ts`): `validateDomain()` re-validates every record before inclusion; failures are excluded with a warning appended to the manifest rather than aborting the whole export.

## Publishing workflow

`lib/publishing/workflow.ts` defines one status graph shared by every domain:

```
draft ──────────────► ready_for_review ──────────────► published
  │                        │  ▲                            │
  └────────► archived ◄────┘  └──────── needs_update ◄──────┘
                 │                           │
                 └──────────► draft ◄────────┘
```

`canTransitionStatus(from, to, guard?)` checks the graph first, then runs an optional domain-specific `guard`. Two guards exist today:

- `legislationPublishGuard(doc)` — delegates to `lib/legislation/readiness.ts`'s `getPublicationBlockers(doc)` rather than re-implementing the rule, so the status-graph guard and the wizard/detail-page checklist can never drift apart. Blocks `-> published` and returns the first blocker as the rejection reason.
- `taxonomyPublishGuard(blockers)` — takes an already-computed blocker list rather than a raw record, since each domain's blocker function needs different cross-domain data (duplicate-key/name checks for taxonomy; relationship/CTA/legal-source checks for Microcards/Rights & Legal Information; contact/relationship/reporting-method checks for the Support Directory) that a generic graph-level guard has no access to. Blocks both `-> ready_for_review` and `-> published` when `blockers.length > 0`. Despite the name (which predates Phase 4), this guard is fully generic — it was never coupled to taxonomy's own shape — and every later phase reuses it as-is (Microcards and Rights & Legal Information in Phase 4; Support Organisations, Advocates & Counsellors, and Reporting Destinations in Phase 5) rather than duplicating it under a second name. Each domain's own eligibility module (`lib/taxonomy/eligibility.ts`, `lib/microcards/eligibility.ts`, `lib/rights-content/eligibility.ts`, `lib/support-directory/*-eligibility.ts`) computes the blocker list this guard receives. **Verification-independent-of-publication is enforced by omission, not by a special guard:** none of the three Support Directory `get*Blockers()` functions ever inspect `verificationStatus`, so `taxonomyPublishGuard` allows `-> published` for an unverified record exactly as it would for any other record with an empty blocker list. An earlier `supportProfessionalPublishGuard()` (an explicit always-allow guard, never actually imported by the repository) was removed in Phase 5 once this was confirmed — it duplicated, and risked misrepresenting, a rule already fully enforced by the blocker list itself.

There is deliberately **no single universal publish rule** — each domain supplies its own guard function.

**A brand-new record's starting status bypasses the graph, on purpose.** `ALLOWED_TRANSITIONS.draft` only permits `ready_for_review` and `archived` — direct `draft -> published` is invalid for an *existing* record, and rightly so (an admin shouldn't be able to silently skip review on content that's already live). But the three taxonomy create forms let an admin choose Publish directly while creating something new, with zero prior state. Rather than creating at `status: "draft"` and then calling `transitionStatus(..., "published", ...)` — which would hit the exact same graph restriction and fail with `StatusTransitionError` — each create handler seeds the new record's `status` field with the chosen target directly (`create()` doesn't run the graph check at all, only `transitionStatus()` does). Editing an *existing* draft still goes through the real `transitionStatus` graph check every time, so the restriction is fully intact for every record that already has a persisted status — it only doesn't apply to the record's very first state.

## Legislation eligibility rules (`lib/legislation/readiness.ts`)

The single source of truth for every "is this record allowed to X" question about a `DocumentRecord`, imported by the wizard, the detail page, the RAG Readiness tab, the row-actions menu, `legislationPublishGuard`, and the export serializer — none of them re-derive these checks independently:

- `getPublicationBlockers(doc)` / `isPublishable(doc)` — the publish gate (file, extraction, required metadata, legal review, no blocking issue). Does **not** require AI permission, license status, or a review date.
- `getAiEligibilityBlockers(doc)` / `isAiEligible(doc)` — published + not archived + AI permission + legal review + successful extraction + no blocking issue. Independent of publication.
- `isReviewOverdue(doc, referenceDate = new Date())` — a pure date comparison; never mutates status. The UI shows an "Overdue for review" badge instead of auto-changing anything.
- `getRagReadinessChecklist(doc)` — the eight-point checklist rendered on the detail page and (per-row, as blockers) on the RAG Readiness tab.
- `getOverallReadiness(doc)` → `"ready" | "blocked" | "awaiting_review" | "processing_issue"` — one classification, driven by the same functions above, used by the RAG Readiness tab's filter buttons.
- `summarizeReadiness(docs)` — pure aggregation, called by both `getRagReadinessSummary()` (repository) and directly by unit tests (no Dexie needed).

## Document extraction orchestration (`lib/legislation/document-extraction-service.ts`)

Three entry points share one internal `commitExtraction()` helper so create/replace/retry can never diverge or duplicate a document:

- `createDocumentFromFile(repository, input, onProgress)` — creates the draft document row first (visible even if extraction then fails), extracts, and commits the outcome either way via `applyExtractionResult`.
- `replaceDocumentFile(repository, documentId, newFile, actor, onProgress)` — extracts the new file; only commits via `applyExtractionResult` on success. On failure, the document is left completely untouched and only an audit event records the failed attempt — the previous valid file and chunks are never destroyed.
- `retryExtraction(repository, documentId, actor, onProgress)` — same commit contract as replace, but reuses the already-stored blob (`documents.getFileBlob`) instead of a newly-selected file.

## PDF pipeline

`lib/pdf/validate-pdf-file.ts` → `lib/pdf/extract-pdf.ts` → `lib/pdf/chunk-text.ts`, called by the extraction orchestration above (in turn used by `components/legislation/steps/step-upload.tsx` for create/replace, and the Processing Issues tab for retry):

1. **Validate**: type/extension + size against `AppSettings.pdfMaxFileSizeBytes`.
2. **Extract**: `pdfjs-dist`, loaded dynamically in the browser, with its worker resolved via `new URL("pdfjs-dist/build/pdf.worker.min.mjs", import.meta.url)` (bundler-resolved static asset) and `standardFontDataUrl: "/pdfjs/standard_fonts/"` pointing at a copy of `pdfjs-dist`'s standard font metrics under `public/pdfjs/standard_fonts/` (copied at setup time — without it, text using a PDF's built-in/non-embedded base fonts can extract incorrectly). Extraction yields to the main thread between pages via `requestIdleCallback`/`setTimeout` so large documents don't freeze the UI.
3. **Chunk**: `chunkExtractedPages()` concatenates page text in order and splits once a running chunk crosses ~900 characters — deterministic (same input → same chunk boundaries), verified by `tests/unit/chunk-text.test.ts`.
4. Failures (`PdfExtractionError`, kind `encrypted | corrupted | empty`) update the document's `processingStatus`/`extractionStatus`/`processingIssue` instead of throwing past the UI — the **Processing issues** tab reads directly off those fields.

## Local retrieval algorithm (`lib/legislation/retrieval.ts`)

`tokenizeQuery()` (lowercase, strip punctuation, drop stop words + single-character tokens) → `scoreChunkText()` (token-occurrence count + a flat exact-phrase-match boost) → `searchLocalChunks()` (filters by jurisdiction/incident category/scope, applies a small `priority`-based boost, sorts by score, truncates to `limit`). Pure functions, no I/O — `tests/unit/legislation-retrieval.test.ts` exercises them directly. This is a keyword-overlap preview, not a ranking algorithm intended for production reuse — see README "Local retrieval test."

## Document form schema (`lib/legislation/document-form-schema.ts`)

`documentFormSchema` (Zod + `react-hook-form`'s `zodResolver`) validates what the admin types across wizard Steps 2–4 — stricter than `documentSchema` (which must accept a bare-minimum draft for storage). `STEP_FIELDS` maps each step to the fields `form.trigger()` validates before "Continue" is allowed to advance. `defaultFormValues(doc?)` builds the form's initial values for both create (all blank) and edit (populated from the existing record) — the same schema and the same step components render both modes; there is no separate edit-only form.

## Content bundle format

See the README's [Content bundle export: Published Content Bundle vs Admin Backup](../README.md#content-bundle-export-published-content-bundle-vs-admin-backup) section for the full manifest shape, the `purpose` split, and the JSON-vs-ZIP distinction. Checksums are SHA-256 over each domain's `JSON.stringify`'d array, computed via `crypto.subtle.digest` (available in both the browser and Node's `node:test` runner, which is what `tests/unit/export-bundle.test.ts` and `tests/unit/content-export-bundle.test.ts` exercise without a browser). `lib/legislation/export-transform.ts`'s `toPublishedLegislationExport()` is the field allow-list applied to legislation records specifically when `purpose === "published_content"`; `lib/microcards/export-transform.ts` and `lib/rights-content/export-transform.ts` are the Phase 4 equivalents for those two domains (see "Microcards & Rights and Legal Information" above), and `lib/support-directory/organisation-export.ts` / `professional-export.ts` / `destination-export.ts` are the Phase 5 equivalents for the three Support Directory domains (see "Support Directory" below). Every one of these transforms preserves `verificationStatus` unstripped on the Support Directory domains — the one field explicitly never treated as "internal," since a Published Content Bundle consumer must be able to show the same "Not verified" state the admin dashboard shows, not silently upgrade a record to implied-verified by omitting the field. `export-bundle-zip.ts` additionally exports a `profile-images/` folder of professional profile images, mirroring the existing `documents/` folder's PDF-export pattern, with a manifest warning when a published professional has no uploaded image rather than a broken reference.

## Taxonomy (`lib/taxonomy/*`, `components/taxonomy/*`)

See the README's [Taxonomy](../README.md#taxonomy-incident-types-triage-labels-resource-categories) section for the product-level rules (machine-key policy, per-entity fields, publish/archive/delete rules, Replace References). This section covers how the pieces fit together.

- **`lib/taxonomy/types.ts`** — `TaxonomyEntity` (`{ id, name, machineKey, status, displayOrder }`), the one shared structural constraint. Every generic taxonomy component (`TaxonomyStatusActions`, `TaxonomyRowActions`, `ReplaceReferencesDialog`), hook (`useTaxonomyRecord`, `useTaxonomyUsage`), and repository interface (`TaxonomyRepository<T>`) is written against this single type — introduced after an early implementation pass where each file declared its own slightly different local structural type and the compiler caught them drifting apart.
- **`lib/taxonomy/machine-key.ts`** — format validation, normalization, and name-to-key suggestion. Pure functions, `tests/unit/taxonomy-machine-key.test.ts` covers the format edge cases (accented characters, digit-leading names, punctuation-only names).
- **`lib/taxonomy/validation.ts`** — `isDuplicateMachineKey`/`isDuplicateDisplayName` (case/whitespace-normalized, `excludeId`-aware for edit-mode self-comparison) and `isValidDisplayOrder`.
- **`lib/taxonomy/eligibility.ts`** — one `commonBlockers()` (name + machine key) plus a `get<Entity>Blockers()` per entity layering entity-specific requirements on top (description for all three; `labelGroup` for Triage Label). This exact blocker list is what `taxonomyPublishGuard` receives, so the form's inline warning, the row-actions disabled state, and the repository's actual enforcement can never disagree.
- **`lib/taxonomy/dependency-service.ts`** — the usage/dangling-reference/replacement-planning engine; see README for what it covers. Deliberately Dexie-free (`TaxonomyDataBundle` is a plain data object) so `tests/unit/taxonomy-dependency-service.test.ts` can exercise every code path — including the singular `matchingRules.incidentTypeId` field being treated as a 0-or-1-element array everywhere else expects an array — without a browser or fake-indexeddb. Phase 4 widened `computeTaxonomyUsage`/`findDanglingTaxonomyReferences` from `TaxonomyKind` (`incident_type | triage_label | resource_category`) to the new `DependencyKind` (`TaxonomyKind | "microcard" | "rights_content"`) — `planReferenceReplacement` (Replace References) deliberately stayed scoped to `TaxonomyKind` only, since neither new domain has that workflow. `buildMicrocardSources`/`buildRightsContentSources` cover the one thing that can reference either today (a Matching Rule's `microcardIds`/`rightsContentIds`, confirmed by grep) — and `buildIncidentTypeSources`/`buildResourceCategorySources` were extended (not duplicated) to also list Microcards/Rights & Legal Information as *referencing* sources, since both already had `incidentTypeIds`/a resource-category relationship from Phase 1. Phase 5 widened `DependencyKind` again to `TaxonomyKind | "microcard" | "rights_content" | "support_organisation" | "support_professional" | "reporting_destination"` and added `buildSupportOrganisationSources()` (Microcards/Rights & Legal Information via `relatedSupportOrganisationIds`, a linked Professional/Destination via `organisationId`, and Matching Rules via `supportOrganisationIds`), `buildSupportProfessionalSources()`, and `buildReportingDestinationSources()` (both Matching-Rules-only today) — `buildResourceCategorySources()` was extended a second time to also list all three new entities as referencing sources.
  - **A real pre-existing bug found and fixed while doing this:** `applyReferenceReplacementPlan()`'s `switch` on `(entityType, kind)` had `"microcard"` / `"rights_content"` / `"support_organisation"` / `"reporting_destination"` cases that wrote unconditionally to that record's `incidentTypeIds` field regardless of what `kind` the Replace References operation was actually for. Every one of those four entity types already carries **both** an `incidentTypeIds` field *and* a resource-category relationship (`resourceCategoryId`/`resourceCategoryIds`), so a resource-category Replace References operation touching any of them would have silently corrupted `incidentTypeIds` instead of updating the resource-category field it was supposed to. This predated Phase 5 for `microcard`/`rights_content` but was only ever exercised by Phase 5's addition of `resourceCategoryIds` relationships and matching seed/test coverage — fixed by branching each case on `kind === "incident_type"` vs. `kind === "resource_category"` before deciding which field to write.
- **`lib/taxonomy/list-filters.ts`** — `TaxonomyListFilters` (status / demo / archived) shared by all three list pages' filter panel and `applyTaxonomyListFilters()`.
- **`lib/taxonomy/resource-icons.ts`** — the curated `iconKey -> @tabler/icons-react component` and `accentToken -> label` maps described in the README; the only place either mapping is defined.
- **`lib/taxonomy/export-transform.ts`** — the three `toPublished<Entity>Export()` field allow-lists used by `export-bundle.ts` for `purpose: "published_content"`; see README's bundle-export section.
- **`components/taxonomy/*`** (flat files) — shared building blocks: `machine-key-field.tsx`, `taxonomy-status-actions.tsx`, `taxonomy-row-actions.tsx`, `taxonomy-filters-panel.tsx`, `usage-summary.tsx`, `replace-references-dialog.tsx`, `reorder-panel.tsx`.
- **`components/taxonomy/<kind>/`** (one subfolder per entity) — `columns.tsx` (TanStack `ColumnDef[]` for that entity's `DataTable`) and `<kind>-form.tsx` (the single-page create/edit form — see below for why this isn't a wizard).

This section covers how the pieces fit together, and — since this module was added directly after taxonomy in Phase 4 — what's shared vs. deliberately duplicated between them.

## Support Directory (`lib/support-directory/*`, `lib/models/support-organisation.ts`, `support-professional.ts`, `reporting-destination.ts`, `verification.ts`, `components/support-organisations/*`, `components/advocates-counsellors/*`, `components/reporting-destinations/*`)

See the README's [Support Directory](../README.md#support-directory-support-organisations-advocates--counsellors-reporting-destinations) section for the product-level rules (verification policy, contact/reporting-method architecture, organisation ↔ professional/destination relationships, profile image, dependency protection). This section covers how the three domains share code without forcing an artificial common shape onto entities with genuinely different fields.

- **`lib/models/verification.ts`** — the one shared verification model: `VERIFICATION_STATUSES` (five states: `not_verified | verification_pending | verified | verification_expired | verification_rejected`), labels, honest non-regulatory descriptions, `isCurrentlyVerified()`, and `isVerificationExpired(expiryDate, referenceDate?)` (a pure date classification, deliberately never called from any write path — expiry is a display-time computation, not something that auto-transitions a stored status). `VerificationBadge` (`components/ui/status-badge.tsx`) is the one shared rendering of this five-state model, reused by every list column, detail page, preview panel, Dashboard, and Review Queue that shows it.
- **`lib/support-directory/contact.ts`** — shared low-level contact logic, not a shared contact *shape*: `isSafeUrl()`/`isInsecureHttpUrl()`/`isValidEmailValue()`, the `safeUrlFieldSchema`/`emailFieldSchema`/`phoneFieldSchema` Zod helpers (the phone schema deliberately has no format regex — it never reformats or rejects a plausible-looking phone number, since Australian phone formatting conventions vary too much to safely canonicalize), `telHref()`/`mailtoHref()`, and three separate `derive*ContactCapabilities()` functions (organisation/professional/destination) rather than one generic one — each entity keeps its own pre-existing flat field names (no nested `contact` object was introduced onto any of them), so the derivation functions are the shared part, not the shape they read from. A capability (`canCall`, `canEmail`, `canVisit`, `canBookOnline`, ...) is always **derived** from whether the backing field is actually populated, never a manually-set boolean a record could get out of sync with its own data.
- **`lib/support-directory/support-organisation-eligibility.ts`** / **`professional-eligibility.ts`** / **`destination-eligibility.ts`** — `get*Blockers(record, context)`, the same role `lib/microcards/eligibility.ts` plays for Microcards: the blocker list fed to `taxonomyPublishGuard`, so the form's inline warnings, the disabled Ready-for-review/Publish buttons, and the repository's actual enforcement can never disagree. None of the three ever inspects `verificationStatus` — see "Publishing workflow" above for why that's the actual mechanism behind "may publish while unverified."
- **`lib/support-directory/organisation-export.ts`** / **`professional-export.ts`** / **`destination-export.ts`** — the three `toPublished*Export()` field allow-lists, mirroring `lib/microcards/export-transform.ts`; see "Content bundle format" above for the `verificationStatus`-is-never-stripped rule.
- **`lib/support-directory/reporting-method.ts`** — `isReportingMethodSupported(method, record)` / `getUnsupportedReportingMethods(record)`: a Reporting Destination may only claim a reporting method (phone, online form, email, in person, ...) that its own contact fields actually back — checked at both the destination-eligibility level (blocks publish) and inline in the form (immediate "Missing contact information for: X" warning), from the same function, so they can't drift apart.
- **`lib/support-directory/profile-image.ts`** — `validateProfileImageFile(file, maxBytes?)`, structurally mirroring `lib/pdf/validate-pdf-file.ts` (type/extension + size check) but restricted to `image/jpeg | image/png | image/webp` — SVG is deliberately excluded, since an uploaded SVG can embed script content and this is the one upload path in the app that isn't a sandboxed PDF text-extraction target.
- **`lib/support-directory/labels.ts`** — `SUPPORT_MODE_LABEL`/`COST_TYPE_LABEL`, small display-label maps shared between the organisation and professional forms/previews (both reuse the same support-mode and cost-type enums).
- **`lib/models/organisation-type.ts`** / **`reporting-destination-type.ts`** — the `ORGANISATION_TYPES` (12 values), `DESTINATION_TYPES` (12 values), and `REPORTING_METHODS` (9 values) enums, plus the shared `TRISTATE_VALUES`/`tristateSchema` (`yes | no | unknown`) used for `anonymousReporting` and `emergencySuitability` specifically instead of a boolean — a boolean can only encode "confirmed yes" or "reads as no," which is unsafe for a field where the honest answer is frequently "we don't know," and reads as a false negative rather than a gap.
- **`hooks/use-profile-image-url.ts`** — `useProfileImageUrl(professionalId, hasStoredImage)`: fetches the stored `Blob` through the repository (never Dexie directly), creates an object URL, and revokes it on every change and on unmount — the same object-URL lifecycle discipline the PDF preview path already required, now with a second consumer.
- **`components/support-organisations/*`**, **`components/advocates-counsellors/*`**, **`components/reporting-destinations/*`** — `columns.tsx` (`ColumnDef[]`), `<entity>-form.tsx` (single-page form + live preview, same reasoning as "Why single-page forms" above), `<entity>-preview.tsx`. Advocates & Counsellors additionally has `profile-image-field.tsx` (upload/replace/remove, initials fallback when no image is stored).

## E2E test infrastructure and a recurring real bug: concurrent `<Link>` prefetch

`scripts/e2e-runner.mjs` owns the whole test-run lifecycle (lock file → build → start a production server on port 3199 → poll for readiness → run Playwright → always tear the server down, including on SIGINT/SIGTERM) rather than relying on Playwright's own `webServer` option, because `next dev`'s per-route first-visit compilation cost made navigation assertions flaky against a dev server. `playwright.config.ts` accordingly has no `webServer` block. `workers: 2` is the highest concurrency proven stable in this project's testing so far — not a value chosen for any principled reason beyond "this many parallel browser sessions against one un-clustered `next start` process held up."

**A confirmed, recurring real bug, not test flakiness:** Next.js prefetches every `<Link>` in the viewport by default. Against this project's single `next start` process (matching a real local administrator's setup — no clustering), a page with many visible `<Link>`s firing that many concurrent RSC prefetch requests at once was confirmed (via network trace) to occasionally starve the very next click's own navigation request indefinitely. First found and fixed on the sidebar nav (`components/layout/sidebar-nav.tsx`, 14 always-visible links) in an earlier phase; Phase 4 reproduced the identical symptom — a click that Playwright's own actionability check reports as "visible, enabled and stable" still timing out at the action-level `15_000`ms cap — on the Microcards/Rights & Legal Information list-page title links, the Dashboard's `StatCard` links (13 on that page), and the Review Queue's Title/View link columns, and fixed it the same way (`prefetch={false}`). This is a genuine, reproducible finding (confirmed across repeated runs going from 4–5 failing smoke tests down to 1), not the same thing as the historical, still-unresolved shell-navigation flake noted below — that one's `prefetch={false}` attempt on the sidebar nav itself was inconclusive (a validation re-run showed *worse* results), and is kept only as a defensible minor performance improvement on its own merits, not a proven fix for that specific flake.

**Known, currently unresolved:** one Microcards smoke test (`tests/e2e/microcards-smoke.spec.ts`, "Add microcard navigates to the create form...") reproducibly hangs on its very first click to a not-yet-visited route in a fresh browser context, across every run since the prefetch fixes above landed, while the other 17 of 18 new smoke tests pass reliably. Not chased further than initial diagnosis, per this phase's explicit scope boundary against broad E2E infrastructure experimentation — see README "Known limitations."

**Phase 5 update — the same flake class, at a higher rate:** `prefetch={false}` was applied proactively this phase everywhere the pattern above calls for it (Support Directory `StatCard`s, table title links, "Add X" page-header links) before the smoke suite was ever run, on the strength of the Phase 4 finding above. Despite that, the first full run of the three new Support Directory smoke spec files still hit 6/26 failures, all on an "Add X" link or a Dashboard `StatCard` link — i.e. still specifically the first interactive click on a freshly loaded page, the same signature as the Microcards case above (Playwright's own actionability check reports the element visible/enabled/stable; only the click's navigation itself times out). A second run after unrelated test-content fixes landed 20/26. Every one of the six routes involved is independently confirmed working by other passing tests in the same suite using `.goto()`, `.fill()`, `.selectOption()`, and edit/delete flows, so this is very unlikely to be a new distinct bug — the leading explanation is that Phase 5's larger demo-data volume and page surface area increased first-paint/hydration cost on a fresh context enough to raise the rate of the same underlying timing sensitivity. Documented rather than chased further, per the same scope boundary — see README "Known limitations."

## Phase 6 — Matching Rules, canonical mock contract, deterministic matching

Phase 6 is a **mock-only** integration boundary: no real AI, no real backend, no live Admin→Frontend sync, no production database. Its job is to make the eventual real integration a drop-in replacement rather than a redesign. Everything below is deterministic and local.

### Matching Rule model rework

`lib/models/matching-rule.ts` was rewritten this phase. Old shape (Phase 3 placeholder): `incidentTypeId` (singular, optional), `active` (boolean), no `machineKey`. New shape: `machineKey` (reuses `lib/taxonomy/machine-key.ts`'s existing lowercase-snake-case/immutable-after-save policy, even though Matching Rules aren't a `TaxonomyKind`), `description`, `priority`, `enabled` (renamed from `active`), `topicKeys: AssistantTopicKey[]` (new — `lib/models/assistant-topic.ts`, the five Assistant routes), `incidentTypeIds`/`triageLabelIds`/`resourceCategoryIds` (all arrays now), `jurisdictions: AustralianJurisdiction[]` (was untyped `string[]`), `urgencyLevels`, `supportNeeds: string[]` (free text — no governed "support need" taxonomy entity exists to ground an enum), the six recommendation-id arrays (`microcardIds`, `rightsContentIds`, `supportOrganisationIds`, `supportProfessionalIds`, `reportingDestinationIds`, `legislationIds` — grouped as `MATCHING_RULE_RECOMMENDATION_FIELDS`), `reviewDueDate`, `internalNotes`, `publishedDate`. `DB_SCHEMA_VERSION` bumped 1→2 with an `.upgrade()` migrating the old shape (this is a local-only IndexedDB with no real users, so the migration favors "never throw" over perfect field-by-field fidelity).

**Every condition array is a wildcard when empty**, not "matches nothing" — a rule with every condition empty is a general fallback rule that always triggers once enabled+published. This is why `jurisdictions: []` means Australia-wide, not "no jurisdiction," matching the same semantic `SupportOrganisation.australiaWide`/`ReportingDestination.australiaWide` already establish elsewhere, just expressed as an empty array instead of a second boolean flag (a rule's own jurisdiction *condition* is a filter, not a content record's own service-area declaration, so the two didn't need the same representation).

### Eligibility (`lib/matching-rules/eligibility.ts`)

`getMatchingRuleBlockers(record, context)` is intentionally **stricter than Microcards/Rights & Legal Information's own eligibility**: every recommendation-id array is checked on *every* call, not just at the moment of new selection — any resolved-but-not-`published` recommendation blocks Ready for Review/Publish, with no "existing relationship grandfathered in" leniency. A matching rule that recommends unpublished content is actively wrong (it would silently point users at content the mock matcher then can't legally include), not just imperfect the way an already-published Microcard with an now-archived related-organisation link is judged elsewhere. Dangling ids (true "doesn't exist at all") still block everywhere, as in every other domain.

### Canonical public mock contract (`lib/contract/published-content-contract.ts`)

One Zod-validated file: `PublishedIncidentType`, `PublishedTriageLabel`, `PublishedResourceCategory`, `PublishedLegislationSource`, `PublishedMicrocard`, `PublishedRightsContent`, `PublishedSupportOrganisation`, `PublishedSupportProfessional`, `PublishedReportingDestination`, `PublishedMatchingRule`, `PublishedMockContentManifest`, `PublishedMockContentBundle`, plus the runtime-matching types `MockIncidentContext`, `MockMatchingRequest`, `MockMatchingResult`, `MockMatchedRecommendation`, `MockMatchReason`. `PUBLIC_CONTRACT_SCHEMA_VERSION = "1.0.0"`, `PUBLIC_CONTRACT_PURPOSE = "published_content"`. Every `PublishedX` type is a field allow-list matching this app's own `toPublishedXExport()` output exactly (enforced by `scripts/generate-mock-bundle.ts`'s `.safeParse()` at generation time, not just trusted).

**No shared workspace exists** between `safespeak-admin` and `safespeak-frontend` (separate git repos, separate lockfiles), so this file can't be imported at runtime by the frontend. Instead it — and `lib/matching-rules/engine.ts`, the deterministic matching engine — are **physically copied byte-for-byte** into `safespeak-frontend/src/lib/contract/` and `safespeak-frontend/src/lib/matching-rules/` by `scripts/generate-mock-bundle.ts`. Both files use a *relative* import (`../contract/published-content-contract`, not the `@/` alias) specifically so the copy resolves correctly in the frontend's own module graph, which has an unrelated `@/*` root — this only works because the generation script preserves the exact same relative directory nesting in both apps.

### `scripts/generate-mock-bundle.ts`

Builds the deterministic Published Content Bundle fixture directly from this app's own `lib/db/seed.ts` arrays (never a second hand-authored catalogue) run through the real `toPublishedXExport()` transforms — the same functions a live "Export Published Content Bundle" admin action calls — filtered to `status === "published"`, then validated against the contract schema (any mismatch between an export shape and the contract fails the script loudly). A matching rule referencing content excluded from this specific export (e.g. a demo record dropped when `includeDemoData: false`) is itself excluded with a manifest warning, mirroring the same policy `lib/bundle/export-bundle.ts` already applies. `GENERATED_AT` is a fixed constant (not `Date.now()`) so re-running the script without a content change produces a byte-identical artifact.

Commands (from `safespeak-admin/`): `pnpm mock-bundle:generate` (write + sync), `pnpm mock-bundle:check` (verify only, exits 1 on drift — suitable for CI). The frontend has its own `pnpm mock-bundle:validate` (`safespeak-frontend/scripts/validate-mock-bundle.ts`) which re-validates the committed bundle against *its own* copy of the schema, rejects an Admin Backup bundle or an unsupported schema version, and checks for duplicate ids / dangling relationships independently of the generator.

### Deterministic matching engine (`lib/matching-rules/engine.ts`)

Pure function, no randomness, no AI, no external calls, no reliance on array order as an implicit rank. `runMockMatching(bundleData, context): MockMatchingResult` is the public entry point (frontend + the ultimate shape Test Matching renders); `runMockMatchingDebug(...)` is a superset used only by the Admin "Test Matching" panel (adds `notTriggeredRuleIds` and `excludedRelationships` — never a second, simplified algorithm, just the same computation with extra fields exposed).

- **Trigger policy**: only `status === "published" && enabled === true` rules are evaluated. A rule triggers when every non-empty condition dimension it declares is satisfied by the context; an empty dimension never blocks. `resourceCategoryIds` is a condition field with no `MockIncidentContext` counterpart, so it is never evaluated at runtime (documented, not silently ignored). An unknown (`undefined`) context jurisdiction only satisfies jurisdiction-agnostic (empty-array) rules — never guessed toward a specific jurisdiction.
- **Ordering**: rule `priority` ascending (lower number wins), then rule `id` ascending as a deterministic tie-break. Never a legal, clinical, risk, or safety score.
- **Deduplication**: a record recommended by two triggered rules appears once, at the position its highest-priority recommending rule established, with every triggering rule's match reasons merged onto it.
- **Result limits**: one central `RESULT_LIMITS` map (microcard 6, rights_content 4, support_organisation 6, support_professional 4, reporting_destination 4, legislation_source 4), applied after dedup — the one place either app's Triage rendering or Admin's preview could apply a different hidden limit, and doesn't.
- A recommendation id that doesn't resolve to any record in the bundle passed in is excluded (never invented) and surfaced via `excludedRelationships` in the debug result.

`lib/matching-rules/build-preview-bundle.ts` (Admin-only) builds a `PublishedMockContentBundle["data"]`-shaped object from the **current live** admin content (not the frozen generated JSON) using the same `toPublishedXExport()` transforms, so Test Matching previews what publishing right now would produce, including a rule not yet exported.

### Admin Matching Rules module

Routes: `/taxonomy/matching-rules` (list), `/new`, `/[matchingRuleId]` (detail + Test Matching panel), `/[matchingRuleId]/edit`. Repository: `matchingRules` upgraded from a bare `CrudRepository<MatchingRule>` to `PublishableContentRepository<MatchingRule>` (status transitions, version-checked updates, draft deletion, usage lookup — the same surface Microcards/Rights & Legal Information/Support Directory already have). `EnabledToggleButton` is a new, small component (Enable/Disable is a boolean orthogonal to publish status, not a status transition itself) that calls `updateWithVersionCheck` and appends its own audit event at the UI layer, since the generic `updateWithVersionCheck` doesn't append one itself. Dashboard gained 7 Matching Rule `StatCard`s; Review Queue now includes `ready_for_review` matching rules using the same `getMatchingRuleBlockers` eligibility function as the form/list/bundle export — one eligibility function, four call sites, never four copies of the same rule.

### Deferred (explicitly out of Phase 6 scope)

Real AI/incident extraction, real backend/API, live Admin→Frontend sync, production database, RAG/embeddings/vector search, external verification, live professional availability/booking, multiple admin roles, full historical E2E stabilisation. `Support Needs` is a lightweight free-text tag, not a governed taxonomy — a future phase may promote it to one if repository evidence justifies it.

## Knowledge & Legislation tab regression (freeze + unstyled page)

Two symptoms were reported against `/content/knowledge-legislation`: Chrome's "Page Unresponsive" dialog when switching tabs, and — after an earlier attempted fix — the page rendering as raw, unstyled HTML.

**Confirmed root cause of both symptoms: a stale/corrupted `.next` dev-build directory**, not a source-code infinite loop. Evidence: an automated Playwright reproduction against the app's then-running dev server showed every dev-mode asset request (`_next/static/css/app/layout.css`, `_next/static/chunks/main-app.js`, `app-pages-internals.js`, `app/layout.js`, `app/content/knowledge-legislation/page.js`) returning 404, while the actual files on disk in `.next/static/chunks/app/` used **production-build hashed filenames** (e.g. `layout-c7b9d457e51e721d.js`) instead of the unhashed dev-mode paths the live dev server was requesting. This is the exact signature of running `next build` against the same `.next` output directory a `next dev` process is concurrently serving from — the dev server's HTML shell keeps referencing dev-mode asset URLs that no longer exist once a production build has overwritten `.next`. With zero JS successfully loading, the browser renders only the unstyled server-rendered HTML (the first symptom) and can end up thrashing (repeated failed module/HMR reconciliation attempts) badly enough to trip Chrome's hang detector (the second symptom, reproduced a second time mid-investigation via the identical mechanism — running the Playwright e2e runner's own `next build` step while a dev server was still live on the same directory).

**Confirmed NOT a source-code infinite loop.** After restarting the dev server cleanly (no `.next` deletion — just the normal dev-server lifecycle), an 80-click/20-round automated stress test across all four tabs produced zero console errors, zero React warnings, no "Maximum update depth exceeded" messages, and consistently sub-300ms tab-switch times. Every hook and pure function involved (`useDocuments`, `useAllDocumentChunks`, `useRagReadinessSummary`, `useCrudList`, `getOverallReadiness`/`getPublicationBlockers`/`getAiEligibilityBlockers`, `searchLocalChunks`, `summarizeReadiness`) was individually audited: no state update during render, no unstable effect dependency, no unbounded/recursive computation, no write-during-read.

**Development-server recovery step that remains relevant:** never run `next build` in the same working directory as a live `next dev` process (including indirectly, via `pnpm test:e2e*`/`scripts/e2e-runner.mjs`, which builds a production bundle into the same `.next` directory). If this collision happens again, stop the dev server and start a fresh one — this is a normal dev-server lifecycle step, not a special "clear the cache" workaround, and it does not touch IndexedDB or any other application state.

**Real, if minor, inefficiency found and fixed (defensive hardening, not the freeze's cause):** `RagReadinessTab`, `ProcessingIssuesTab`, and `LocalRetrievalTab` each independently called `useDocuments()` on their own mount. Because the shared `Tabs`/`TabsContent` component (`src/components/ui/tabs.tsx`) already unmounts inactive panels (`if (!selected && !forceMount) return null` — confirmed correct, not something that needed fixing), every tab switch tore down and recreated up to three separate Dexie live-query subscriptions instead of one. `src/app/content/knowledge-legislation/page.tsx` now reads `useDocuments()` once and passes `documents` down as a prop to all three tabs.

**Separately confirmed and fixed: page-level horizontal overflow on narrow viewports.** `TabsList` (`inline-flex`, no wrap) is a flex item inside the shared `AdminShell`'s `flex flex-col` column; a flex item's default `min-width: auto` let its intrinsic content width (four tab labels, ~423px) push the whole page wider than a 390px mobile viewport instead of scrolling within its own bounds. `TabsList` is used nowhere else in the app yet, so this was a zero-blast-radius, page-scoped fix: added `max-w-full overflow-x-auto` to the tab row itself (mirrors the same pattern `DataTable` already uses for wide tables). Desktop/tablet appearance is unchanged (the row already fit without scrolling there); verified via computed-style/`scrollWidth` assertions at both 1366×768 and 390×844.

### Matching-rule/context parity

`Support Organisations`/`Microcards`/etc. condition on Triage Label and Incident Type **ids**, which the deterministic engine can only satisfy if the frontend's topic registry resolves the right **machine keys** into those ids. Audited against the real seeded taxonomy (`online_harassment`, `workplace_discrimination`, `hate_speech` incident types; `immediate_danger`, `escalate_to_authority`, `needs_follow_up`, `religious_bias_indicator` triage labels) and corrected `safespeak-frontend/src/lib/mock/topic-registry.ts`'s candidate machine keys, which had drifted from invented values (`"safety_concern"`, `"escalate_authority"`, `"bias_indicator"`, `"racial_harassment"`, …) that never matched anything actually seeded. ### Build output isolation

**Confirmed root cause** (same one already diagnosed under "Knowledge & Legislation tab regression" above, now permanently fixed rather than only manually recovered): `next dev`, a plain `next build`/`next start`, and the E2E runner's own `next build`/`next start` all defaulted to the single `.next` directory. Running any build while a dev server was live overwrote the dev server's in-flight dev-mode manifest with production-hashed asset filenames the dev server was never going to request — every CSS/JS chunk request then 404'd, which is what produced both the raw-unstyled-HTML and the Chrome "Page Unresponsive" symptoms.

**Fix — Option A from the task brief (separate `distDir` per purpose), not process detection**: `next.config.mjs` now reads `distDir: process.env.NEXT_DIST_DIR || ".next"`. `scripts/run-next.mjs` (new, no new dependency — a direct `child_process.spawn`, never through a shell, matching the same reasoning already established in `scripts/e2e-runner.mjs`) sets `NEXT_DIST_DIR` before invoking the real `next` CLI:

| Purpose | Directory | package.json script |
|---|---|---|
| `next dev` | `.next-dev` | `pnpm dev` |
| production `next build`/`next start` | `.next-build` | `pnpm build` / `pnpm start` |
| E2E `next build`/`next start` | `.next-e2e` | `pnpm start:e2e`; `scripts/e2e-runner.mjs` sets the same env var directly on its own two spawn calls |

Ports are unchanged (dev 3100, E2E 3199). **Live-verified**, not just structurally asserted: started `pnpm dev`, confirmed `.next-dev/` created and the dev server serving correctly; ran `pnpm build` while it was still live — `.next-build/` was created, `.next-dev/` was untouched, and the live dev server (including a full Knowledge & Legislation 20-round/80-click tab stress test) remained fully responsive throughout; then ran `node scripts/e2e-runner.mjs tests/e2e/knowledge-legislation-tabs-smoke.spec.ts` (its own full build+start+test+teardown cycle) while the dev server was *still* live — `.next-e2e/` was created, both E2E tests passed, the E2E server was torn down cleanly afterward, and the dev server was unaffected throughout. `tests/unit/build-output-isolation.test.ts` pins the configuration (distinct directory names, no shell spawn, both `e2e-runner.mjs` spawn calls using the isolated env, `.gitignore` coverage) as a fast CI-safe regression guard for what those manual runs proved.
